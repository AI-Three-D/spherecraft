Here's a dense ruled-out summary for Fable — paste this alongside your problem description:

Context: WebGPU planetary terrain renderer, GPU quadtree LOD system (core/world/quadtree/). Two symptoms: (1) a static, never-blending seam between LOD4 (live splat texture) and LOD5 (prebaked resolvedColor) — resolvedColor reads as invalid (alpha<0.5) on LOD4 tiles 100% of the time, confirmed via a debug mode that forces LOD4 through LOD5's exact rendering path; (2) tiles visibly flicker between high-res and low-res for a few seconds after appearing, sometimes cycling through multiple variants. Repo: AI-Three-D/spherecraft, branch codex-restart, latest relevant commit e41950c.

Ruled out for the seam (resolvedColor always invalid on LOD4), with inference:

Wrong LOD boundary being targeted — ruled out. nearMaxLOD: 4 / resolvedColorStartLod: 5 confirmed in wizard_game/runtimeConfigs.js; a debug edge-highlight mode confirmed the visible seam lines up exactly with the LOD4/5 boundary.
Distance/fade-threshold mistuning — ruled out. A debug mode dumping raw vDistanceToCamera in order-of-magnitude buckets showed sane real-world values (1-10km at test altitude), not garbage. Several different fade windows (absolute meters, chunk-relative, tighter bands) were all tried with zero visible change — consistent with the blend never actually executing, not a wrong number.
Stranded refinement (\"not relevant at dequeue, never retried\") — real bug, found and fixed in tileStreamer.js (_retryVisibleDroppedRefinements, new retry map gated on strict current-frame visibility). Did not change the symptom. Telemetry showed the stuck-tile count (visibleDropRetryMap) frozen/unchanging for many ticks even while 121 tiles were genuinely visible — meaning the specific seam tiles are very likely NOT among the stranded population; they're probably already marked REFINED.
Array-pool layer-reuse ghost-write (stale pending GPU copy from an evicted tile landing on a reused layer after a new tile already committed correct data) — real bug, fixed in TileArrayPool.releaseLayer() (purges pending copies targeting a layer at release time). No visible change to the seam.
resolvedColor bake silently skipped (the dispatch in core/world/terrain-generator/webgpuTerrainGeneratorBatching.js gates the bake behind splatPass.resolvedColorTex && .tileTex && .atlasTexture && .tileTypeLookup all being truthy, with no error if not) — instrumented with a one-time warning log; never fired. Ruled out.
Bake shader itself producing invalid output (core/world/shaders/webgpu/resolvedTerrainColorCompute.wgsl.js) — read in full. Every invocation unconditionally writes textureStore(outputColor, coord, vec4(color, 1.0)) with no branch that could skip the write or leave alpha at 0. Looks correct.
GPU dispatch ordering (resolvedColor's bake reading splat textures before they're written) — checked in webgpuTerrainGeneratorBatching.js: splat generation and the resolvedColor compute pass are separate, sequential passes within the same command encoder — correctly ordered, no race.
Array-pool layer/index mismatch (resolvedColor using different layer numbering than other texture types) — ruled out. TileArrayPool is constructed once with this.streamedTypes (includes resolvedColor) and a single shared tilePoolSize — one unified pool, same layer index means the same tile across all texture types.
Not yet checked for the seam — the most promising remaining lead: something in the fragment-shader-side sampling/addressing (sampleResolvedTerrainColorLevel / applyChunkAtlasUV, in core/renderer/terrain/shaders/webgpu/terrainChunkFragmentShaderBuilder.js) that's specific to how LOD4 instances address the resolvedColor array texture, OR the GPU-side instance builder's ancestor-fallback logic (core/world/quadtree/instanceBufferBuilder.wgsl.js — not inspected at all this session; comments elsewhere describe it as \"walks up the quadtree to the nearest loaded ancestor\" for unloaded leaves, which could plausibly source the wrong layer for an LOD4 instance in a way that's deterministic, not racy).

Ruled out for the flicker:

FPS/speed-adaptive LOD scale injecting threshold noise — ruled out. Telemetry showed lodScale (speed-based, diagnostic-only) fluctuating wildly even while stationary, but visibleScale (the value that actually feeds the traversal threshold) stayed locked at 1.00 throughout every log line.
Stateless quadtree traversal with no hysteresis at the subdivide/merge threshold (shouldSubdivideWithCenter in core/world/quadtree/quadtreeTraversal.wgsl.js) — confirmed stateless (full BFS recomputed from scratch every frame, no per-tile memory of prior decision). Applied a quantization dead-zone fix; zero visible change to the flicker.
Duplicate geometry commit overwriting already-refined data — ruled out. _commitTile in tileStreamer.js has an explicit guard: if (this._tileInfo.has(key)) { ...; return false; } — a second geometry commit for an already-resident tile is rejected, not applied.
Non-deduped request pathway (e.g. predictive/prewarm requests bypassing the normal dedup) — ruled out. Every tile-request call site (VISIBLE, FEEDBACK, PREDICTIVE) routes through the same _queueTile → AsyncGenerationQueue.request(), which dedupes by key (confirmed by reading core/world/asyncGenerationQueue.js).
Array-pool ghost-write race — same fix as above (shared with the seam investigation); no visible change to flicker either.
Not yet checked for the flicker: eviction-protection lag — tile eviction uses pure LRU (_selectEvictionCandidate in tileStreamer.js) with a separate \"protect currently-visible\" set (_protectedKeys) that only updates on a periodic GPU visibility readback (_maybeReadbackVisibleTiles in core/world/quadtree/gpuQuadtreeTerrainRuntimeDiagnostics.js), not every frame. A tile that just became visible but hasn't been confirmed by the next readback yet is unprotected and could be LRU-evicted, then immediately re-requested once the next readback catches up — a plausible evict-reload cycle, not yet verified.
