# Tile streaming / loading performance — preliminary findings (2026-10-01)

**Status:** Opened as a side investigation while debugging the LOD4→LOD5 color seam (see `lod4_lod5_seam_findings_v2.md` and the ongoing mode-100/101/102/103 work). Deliberately parked here — not pursued further this session — because it does not appear to be the direct cause of the seam/fade problem and was starting to pull focus from it. Pick this up as its own task.

## Symptom (user-reported)
- Initial game load takes a long time.
- Even after load, it takes roughly **10-15+ seconds** for tile loading to "settle" (stop visibly changing).
- Separately, already-loaded **high-detail tiles visibly flicker**: a high-res tile appears, then is sometimes replaced by a lower-res variant for a short delay, then reverts back to high-res. Described as happening "quite often," lasting a few seconds per occurrence. User suspects a race condition and/or tiles being queued multiple times (e.g. a low-res request followed by a high-res request for the same tile).
- User's expectation, based on recent work this session decoupling texture generation from height generation (so LOD5+ uses cheap prebaked/simplified textures instead of full compute): **this should have made things faster**, since only a small fraction of nearby tiles should ever need full LOD4-or-finer detail. The fact that it's still slow "does not add up" and deserves its own investigation.

## What was actually measured (real console telemetry, not guesses)

Captured via the existing periodic `[QTLight]` log (see `core/world/quadtree/gpuQuadtreeTerrainRuntimeDiagnostics.js`) plus a one-off instrumentation addition described below. The user flew to a spot with a visible LOD4/5 seam, stood still 5-10s, flew further, stood still 10+s again, and captured the log across that whole sequence.

- **`requestToResident` queue-wait latency climbed continuously across the whole capture**: p50 went 2867ms → 8264ms → 11963ms → 17089ms → 22131ms → 25814ms, with a **max of 36,274ms** (over 36 seconds) for some tile to go from requested to resident. This did not reset or improve during the "stand still" periods — it kept climbing, implying a backlog that had already been created (most likely by the initial fly-to) and simply takes a very long time to drain, even with no new demand being added.
- **`pendingGen` (generation queue depth)** started at 684 and gradually drained to 0 over roughly the whole captured window (with a mid-sequence bump back up to 238 when the user flew further), consistent with a large one-time backlog from view changes that takes many seconds to work through.
- **`queueDropped` (generation queue overflow)** spiked to very large numbers partway through the capture: 121, then 1041, then 1067, then 504, then 109. These are requests the generation queue couldn't even hold and discarded outright (queue-full drops, distinct from the refinement "not relevant" drops below).
- **`wastedGenerations`** (tiles generated but no longer relevant/committed by completion) was nonzero throughout: 22, 55, 40, 92, 14, 11, 8 across the windows — real wasted GPU work, though not enormous relative to the backlog size.
- **An apparent "265x request amplification" (`requested=74898 newlyVisible=282`) was investigated and retracted as a false lead.** `_queueTile()` increments `_requestedTilesWindowCount` on every call, including re-affirmation calls for a tile that's already pending in the queue (e.g. from per-frame feedback/prefetch re-evaluation). `core/world/asyncGenerationQueue.js`'s `request(key, ...)` was read directly and **does correctly dedupe by key** — a repeat request for an already-pending key just promotes its priority in place and returns the existing promise; it does not create duplicate queue entries or duplicate GPU work. So the large "requested" counter reflects a backlogged tile being *touched* many times per second while it waits, not actual duplicate generation. This is a telemetry/metric artifact, not a functional bug — but it did initially look alarming and cost some investigation time before being ruled out. **If this counter is kept, it should probably be reframed (e.g. "touches" vs "distinct admits") to avoid this confusion in future sessions.**

## Refinement-drop-by-depth instrumentation (added this session)

Added to test whether LOD4-depth tiles are specifically/disproportionately starved of refinement (which produces `resolvedColor`) compared to other depths — this was the leading hypothesis for why `resolvedColor` reads as permanently invalid on LOD4 tiles (see the seam findings doc).

- **New counter**: `core/world/quadtree/tileStreamer.js`'s `_refinementDropByDepthWindow` (a `Map<depth, count>`), incremented at the existing "drop as not relevant, don't retry" site in `_queueRefinement`'s inner task (~line 2127). Surfaced through `consumePressureWindow()` as `refinementDroppedByDepth`, and logged in `[QTLight] refinementDroppedByDepth d<depth>:<count> ...` lines by `gpuQuadtreeTerrainRuntimeDiagnostics.js`. This instrumentation is left in place (harmless, low-overhead, only logs when something actually drops).
- **Result**: drops were scattered across many different depths across the captured windows — d0, d1, d2, d3, d4, d5, d6, d11 all appeared at one point or another, not concentrated on whichever depth corresponds to geomLOD4. **This does not support a depth-4-specific structural exclusion.** It looks more consistent with general backlog pressure affecting whatever tiles happen to be marginal (just gone off-screen, or not-yet-relevant) at any given moment, regardless of depth.
- **Open question this leaves**: if it's not depth-specific, why does mode 102 (forcing LOD4 through the exact LOD5 resolvedColor-path) show `resolvedColor` as invalid **100% of the time, uniformly across the whole visible LOD4 area**, rather than patchily? A pure "general backlog, somewhat random" explanation would predict at least some LOD4 tiles having had time to refine, especially ones that have been in view for a while (e.g. if the user stood still for 10+ seconds at a spot before testing). This tension is unresolved — it's possible the mode-102 test wasn't re-run after a long enough idle/settle period, or there's still something depth/priority-specific that this particular instrumentation isn't capturing (e.g. refinement admission priority structurally deprioritizing LOD4 behind other traffic, even without an outright "not relevant" drop).

## User's specific suspicions, not yet investigated
1. **Tiles may be queued multiple times** — e.g. a low-res request followed shortly by a high-res request for the same tile, rather than one request that progressively refines. Not checked this session. Would be worth checking whether `_queueTile` / `_queueRefinement` can end up issuing what are effectively two separate "tiers" of request for the same tile address in a way that causes visible back-and-forth rather than a clean one-way refinement.
2. **The flicker (high-res → low-res → high-res) suggests a race condition**, not just slowness. A pure backlog/slowness story explains "takes a while to get detailed," but not "was already detailed, then visibly got less detailed, then got detailed again." That pattern implies something is actively *regressing* a tile's displayed resolution temporarily — e.g. an array-pool layer being reused/reset while still referenced by a live draw, or a geometry re-generation (LOD re-assignment) transiently reverting to a coarser fallback before the finer result lands. The seam-findings doc's §4 candidate 3 ("array-pool reuse race," citing `_pendingCopies` entries having no owner/generation tag and `releaseLayer` not purging pending copies for that layer) is a plausible mechanism for exactly this and has not been investigated.
3. **The user's expectation that recent work (decoupling texture generation from height generation, so LOD5+ gets cheap prebaked textures) should have made this faster has not been reconciled with the observed numbers.** Worth checking in the next session whether that decoupling actually reduced the *geometry* queue's workload (the numbers above are from `pendingGen`/the geometry queue, not just refinement) — if most of the backlog is in geometry (height/normal/tile) generation rather than texture/refinement, the texture-side optimization wouldn't necessarily show up in these particular metrics at all, which could explain the "doesn't add up" feeling.

## Recommended next steps (for a future session, not this one)
1. Re-run the same capture after a genuinely idle, fully-settled period (watch for `queueDepth=0`, `refinementQueueDepth=0`/`active=0`, and `tileStates` with a high `REFINED` count and near-zero `REQUESTED`/`RESIDENT`-not-refined) to get a clean baseline, rather than during/shortly after active flying.
2. Investigate the array-pool reuse race (`TileArrayPool`/`_pendingCopies`/`releaseLayer` in `tileStreamer.js`) as the leading candidate for the flicker, since it's a plausible mechanism and already flagged in the seam-findings doc without being checked.
3. Separate out geometry-queue load vs refinement-queue load in the telemetry to evaluate whether the texture/height decoupling work actually reduced the *generation* (not just refinement) backlog as expected.
4. Consider reframing or renaming `requestedTiles`/`requestAmplification` in the telemetry so a backlogged tile being re-touched every frame doesn't masquerade as "75,000 requests."
